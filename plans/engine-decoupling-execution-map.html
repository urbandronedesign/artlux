What actually runs on the CPU and the GPU while a show is playing

ArtLux is a multi-process application with seven kinds of OS thread — and one of them does almost all of the work. This page traces a single frame across every executor in the app, so you can see which work is genuinely parallel, which is queued behind something else, and which lane runs out of budget first.

1
CPU core the per-frame content pipeline can use. Composite, atlas, GPU submit, universe packing, encode, the timeline transport, the projector pump, the 3D scene and every React commit all execute on the renderer's single main thread. There are no workers.
7 kinds
Genuinely concurrent executors: renderer main thread, GPU, Node main-process loop, the libuv pool, the Rust send thread, per-port serial writers, and the JUCE audio thread — plus one main thread per projector window.
900 ms
Renderer freeze the wire survived unchanged: 178 packets/s against 226 idle, worst gap 45 ms. Art-Net does not depend on the UI thread — the Rust pacer re-sends the last frame. The picture stops; the show does not go dark.

Read the shape, not the widths

The block order, the row each one sits on, and the fact that the top row is one unbroken queue are all read directly out of the source. The block widths are proportional estimates chosen to make the serialisation legible — the app has no per-block profiler. Every number quoted in the readouts and the findings below is measured, and says where it came from.

The one thing the diagram cannot show is that the GPU readback is asynchronous. The compute pass writes to a staging buffer and mapAsync resolves later, so mapper.read() returns the previous frame's LED bytes. The pipeline is one frame deep by design, and universe packing never waits on the GPU.

Replacing the estimates with measurements
Is the GPU saturated, or starving?

Intel PresentMon

open source · overlay · no instrumentation

Its GPU Busy counter is the time the GPU actually spent executing a frame's commands. Beside CPU frame time, the balance reads directly: GPU Busy well under frame time means the GPU is starving and the bottleneck is the queue in the top row. Five minutes, and it often ends the investigation. Nothing in the app can answer this — it requests no timestamp-query feature, so there is no GPU timing anywhere in src/.

What is the renderer main thread doing?

Chromium tracing → Perfetto

open source · attaches over CDP · changes nothing in the app

npm run profile:trace -- --duration 15 --label context-switch drives the browser-level Tracing domain and writes a file ui.perfetto.dev opens. You get every Chromium thread on one timeline — so the top row of this diagram stops being an argument from source and becomes something you read off a flame chart, with each FireAnimationFrame named and every forced synchronous layout marked.

First capture, 2026-07-29 — 8 s of an idle dev editor: 483,680 events across 44 threads, 3,401 FireAnimationFrame slices at p50 0.09 ms · p99 2.06 ms · max 15.18 ms. That is the per-callback resolution the block widths above are standing in for. Budget ~11 MB per second of recording.
Which GPU dispatch?

RenderDoc

open source · deep dive only

Captures WebGPU through Dawn, with sharp edges: D3D12 only on Windows, F11 to switch the capture API, and it captures every frame rather than on demand. Right tool for a fill-rate question — which is what the beam budget turned out to be — and the wrong tool for anything routine.

None of the three sees the native threads. The Rust pacer, the ENTTEC writers and the JUCE audio callback are not Chromium threads and emit no trace events; they are also the threads that have never been the problem, and artlux_output_* on /metrics already covers them. One timeline spanning native and Chromium threads would mean ETW — free, but not open source. Full runbook, including the seven ways profiling has lied in this repo: docs/DEVELOPMENT.md → Profiling.

Ranked by how much headroom they cost
Critical · structural

The renderer main thread is the pipeline

src/renderer/engine/frameEngine.ts · services/timeline.ts · App.tsx · Simulator3D/

Five independent requestAnimationFrame loops — the frame engine, the timeline transport, the projector pump, the 3D scene and React's own work — share one thread with style, layout and paint. Nothing here runs in parallel with anything else here. There are no *.worker.ts files in the tree: the worker phase is deliberately parked.

measured (WP-0.M, 2026-07-29): under UI load frame p99 168 ms, long frames 47 / 240 — and moving React's cost to zero left it unchanged (155 → 168). The load-case hitching is the context switch plus forced synchronous layout, not React commits.
measured: a context switch costs 70–105 ms, once; a timeline clip drag still costs 330–380 ms/s, of which ~10 ms per render is Timeline's own element tree.
Serious · measured

GPU texture upload and fill rate, not draw calls

src/renderer/gpu/WebGPUMapper.ts · Simulator3D/

Every LED sample is one WGSL compute dispatch — cheap. What costs is getting pixels to the GPU: each copyExternalImageToTexture is a fixed GPU-process sync stall, and under projector contention those stalls dominated. The fix was to compose all surfaces into one atlas on the CPU and upload once, collapsing N uploads and N submits into one of each.

recorded history: the surface-atlas change took the app 16 → 60 fps. The moving-light beam budget turned out to be fill rate, not draw calls — the CPU was optimised first and made it worse. HAP decode once collapsed 61 → 22 → 61 fps.
Serious · structural

The projector pump allocates an ImageBitmap per surface, per window, on the hot thread

src/renderer/App.tsx — the 33 ms pump

Every streamed surface is re-encoded with createImageBitmap — roughly 8 MB at 1080p — then transferred to each projector window's MessagePort. It runs on the same thread as the frame engine, at up to 30 Hz, multiplied by the number of open outputs. Three guards keep it from compounding: an inFlight set for back-pressure, a sentGen map keyed by generation and port so repeated frames are skipped, and a once-per-transition idle notice.

structural: cost scales with (streamed surfaces × open projector windows), and every byte of it is paid on the one thread that also packs universes.
Warning · unverified

HAP decode shares a FIFO pool that may still be four threads wide

src/main/threadpool.ts · native/hap/src/lib.rs

Native HAP decode runs as napi-rs AsyncTasks on the libuv pool. Node's default is four threads and the pool is FIFO and shared, so six 1080p HAP surfaces at three in-flight decodes each can queue ~18 jobs behind one another — surfacing as a decode-ahead ring missing its exact frame, not as an error. The pool is requested at 12.

caveat recorded in the source: libuv fixes the pool size at first use, so if anything in Electron's startup touched it first the request silently does nothing, and it is not observable through any API. The honest check is a 6-source soak comparing missRate at 4 versus 12.
Warning · structural

Live video receive is polled on the same event loop that serves the tablet

plugins/spout · plugins/ndi · src/main/transport/

Spout and NDI are each drained by a 16 ms setInterval in the main process, then copied across IPC into the renderer. That loop is also handling Art-Net input, OSC — including the 61 fps LiDAR blob protocol — the show-control HTTP and SSE server, the metrics endpoint and the watchdog's 1 Hz health tick. It is a second single thread, and two live sources plus a tablet remote all contend for it.

structural: a receive path that misses its poll drops a frame quietly; there is no back-pressure signal from the renderer.
Healthy · measured

The wire is already immune to the UI

native/output-engine/src/lib.rs · serial.rs

A dedicated Rust thread owns the UDP socket and paces transmission, woken by a condvar when JS pushes a frame; push_frame is one memcpy. It re-sends the last frame as keep-alive, so a stalled renderer costs picture, not output. Each ENTTEC USB port gets its own writer thread behind a single-slot mailbox, so a slow or unplugged widget can never stall the network pacer.

measured (WP-3.M): during a deliberate 900 ms main-thread freeze — 172 packets over 967 ms (178/s vs 226/s idle), worst inter-packet gap 45 ms. Three rounds of full context tours plus forced reflow produced zero gaps over 100 ms.

So: are we multithreaded?

Yes at the process level, and no where it counts. The parts of the app that protect the show are properly isolated on their own OS threads — the wire, USB DMX, audio, and HAP decode all keep running through anything the UI does, which is why a 900 ms freeze cost 45 ms of jitter and nothing else.

The parts that make the picture are not. Everything from reading a video frame to putting bytes in a universe buffer runs on one core, and adding surfaces, projector outputs, 3D fixtures or timeline complexity all draws from the same 16.67 ms. That is the ceiling, and it is the reason the measured load-case p99 did not move when React's cost was taken to zero: the queue is the problem, not any one thing in it.

The known way off it is the parked worker phase, and it is blocked by one concrete fact rather than by the platform: a Worker in this Electron build already has WebGPU with an acquirable device, OffscreenCanvas, VideoFrame, VideoDecoder and WebGL2. What it cannot have is a <video> element, which is still the fallback producer for both surfaces and timeline layers. The measurement taken at that fork says a worker would buy smoother content under load, not show survival — the native pacer already provides survival.
